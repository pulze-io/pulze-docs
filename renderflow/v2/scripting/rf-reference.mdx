```python
import renderflow as rf
```

The module a [Python step](/renderflow/v2/scripting/python-steps) and a [plugin](/renderflow/v2/scripting/plugins) both import. Standard library only, and Python 3.8 syntax, because a render node runs it under whatever interpreter it resolved with nothing installed.

## Declarations

Each one is a field in the submitter and the value, from a single line. In a plugin, these are what generate the operator's UI automatically. Every declaration takes `label` (what the submitter shows), `required` and `show_if`, and all of them except `rf.sequence` take a `default`.

| | |
|---|---|
| `rf.text(name)` | A line of text |
| `rf.int(name)` | A whole number. Also `min`, `max`, `step` |
| `rf.float(name)` | A number. Also `min`, `max`, `step` |
| `rf.bool(name)` | A switch. `default=False` |
| `rf.choice(name, choices)` | One of a list. A numeric choice comes back a number |
| `rf.file(name)` | One file. `filter="*.exr"` sets what the browser offers |
| `rf.folder(name)` | One folder |
| `rf.pairs(name)` | Key-value rows, as a dict |
| `rf.resolution(name)` | A width and a height, as a two-item list |
| `rf.output(name)` | Where the job writes. See below |
| `rf.frames(name)` | A frame range. `rf.expand()` turns it into a list |
| `rf.sequence(name)` | An earlier step's output or a browsed file sequence, as a list of files. See below |
| `rf.args(name, type=...)` | The escape hatch every one of the above compiles to |

One rule the module enforces by raising at import: **one output per script**. A second is a mistake worth finding immediately rather than at dispatch.

`show_if` hides a field until another holds a value: `rf.text("codec", show_if={"encode": True})`.

### output

```python
out = rf.output("output", extensions=["png", "exr"], required=True)
```

With `extensions`, the submitter's browse button becomes the operating system's save dialog offering those types, the value is a file path, and the extension you get reads back as `rf.paths.format`. Without `extensions` the output is a folder.

`rf.paths.output` carries the value, which is how a handler downstream knows where the job wrote.

### sequence

```python
frames = rf.sequence("frames", required=True, label="Frames")
```

In the submitter the field is a list of the outputs the earlier steps in the job declare, and a browse button. Pick a step's output, or browse to one frame of a sequence and RenderFlow finds the rest of it beside that frame.

The script always reads a list of paths, already mapped for the machine it runs on with `rf.path()`. A browsed `shot.####.exr` gives every frame of its range. A step's output gives the files that step wrote, filled in when the task starts. Before that, in `@rf.submit` and `@rf.tasks`, the list is empty, because the step it reads has not run yet.

A file in the list that does not exist, such as a frame the earlier step failed to write, is still in the list. Check with `os.path.isfile()` before reading it.

## Hooks

| | Runs |
|---|---|
| `@rf.execute` | Once per item, on the machine that got it. The only one a script needs |
| `@rf.tasks` | On the submitting machine, before the job exists. Returns the work list, one entry per task |
| `@rf.submit` | On the submitting machine, before the job exists. Raise to stop the submission |
| `@rf.prepare` | Once per task, before its items |
| `@rf.cleanup` | Once per task, whatever happened |

### Planning the tasks

`@rf.tasks` is what turns one script into many. It returns a list, and every entry becomes one task:

```python
@rf.tasks
def plan():
    return [{"shot": "010", "camera": "shotcam"}, {"shot": "020", "camera": "witness"}]
```

An entry is anything JSON can carry, and it reaches `@rf.execute(item)` exactly as it left, so a task can be a frame, a file, or a whole description of what that one machine should do. Two helpers cover the ordinary cases:

| | |
|---|---|
| `rf.expand("1-3,7")` | A frame range as `[1, 2, 3, 7]`. A list or a single number passes straight through |
| `rf.list(folder, "*.exr", recursive=False)` | The matching files in a folder, sorted, mapped through `rf.path()` |

It runs on the machine that is submitting, because the farm needs the list before it can make anything. Raising stops the submission with your message; returning an empty list is refused, since a job with no tasks never finishes. Without `@rf.tasks`, a script runs once on one machine.

### Distributing the work

Called on the decorated `@rf.execute` function, to say how its calls should be spread:

```python
@rf.execute
def one(item):
    ...

one.map(batch=False, on_error="stop")
one.once()
```

| | |
|---|---|
| `map(batch, on_error)` | Run `one` once per planned task, chunked across as many machines as the farm gives it. `batch=True` hands a machine its whole slice in one call instead of one item at a time; `on_error="continue"` finishes the rest of a slice before failing it |
| `once()` | Run `one` a single time over the whole list, on a single machine |

Call none of these and the farm decides, which is one task per planned entry.

## Context

Attribute access over what the task was given.

| | |
|---|---|
| `rf.job` | `.id` `.name` `.status` |
| `rf.step` | `.id` `.name` `.index` for the running step |
| `rf.step[0]`, `rf.step["Render"]` | Another step, by position or name |
| `rf.step[i].input` | The file that step runs |
| `rf.step[i].output` | The files it produced, as paths |
| `rf.step[i].type` | Task type, such as `3dsmax.render` |
| `len(rf.step)`, `for s in rf.step` | The job's steps, in order |
| `rf.task` | `.id` `.index` `.attempt` |
| `rf.node` | `.id` `.name` `.software` |
| `rf.paths` | `.temp` this task's scratch folder, `.repo` the repository, `.output`, `.format` |
| `rf.env` | What the step was given |

`rf.step[...]` raises `KeyError` for a name the job does not have, which is the right answer when a script is wired to a step that has since been renamed.

## Resolving

| | |
|---|---|
| `rf.path(value)` | A path as **this** machine sees it, through the rules in **Settings → Mapped Paths**. A path no rule covers comes back unchanged |
| `rf.app(name, version=None, path="exe")` | An installed application's executable. Raises `AppNotFound` |
| `rf.tool(name)` | What RenderFlow ships: `ffmpeg`, `ffprobe`, `imager`, `python`. Falls back to `PATH` |

`path` picks which of an application's binaries to resolve: `rf.app("cinema4d", path="cmd")` returns Cinema 4D's Commandline build rather than its `exe` interface build.

## Reporting

| | |
|---|---|
| `rf.progress(percent, info=None)` | 0 to 100, clamped. The driver already reports per-item progress |
| `rf.log(message, level="info")` | One line into the task log. `print()` works too |
| `rf.fatal(message)` | Stops the step with a reason. Raises `rf.Fatal` |
| `rf.done(item)` | Marks one item finished. Only meaningful under `batch=True`, where the module cannot see your loop |

## Failures

| | |
|---|---|
| `rf.Fatal` | Stop the step, with a sentence the operator reads. **Its other tasks fail too**, and the job stops unless a later step runs on failure |
| `rf.AppNotFound` | This machine cannot do it. **The task moves to another machine**, and the job carries on |

The difference between the first two is the whole of the retry behaviour. `Fatal` is the script saying the work is wrong; `AppNotFound` is the script saying the machine is wrong.

## Exit codes

What the process leaves, and what the farm does with it:

| | |
|---|---|
| 0 | Done |
| 1 | Failed. The step stops: its other tasks fail too |
| 2 | No `@rf.execute`, so a node had nothing to run. The step stops, as for 1 |
| 66 | `AppNotFound`. The task is requeued on a different machine |

## Markers

The module writes these to standard output, and the service reads them. You never write them yourself, and they are here because they show up in a task log:

| | |
|---|---|
| `RF_PROGRESS <n>` | A percentage |
| `RF_ITEM` | One item started, finished or failed |
| `RF_ERROR` | A reason, and a traceback when there was one |
| `RF_DONE` | The slice finished |
| `RF_SCHEMA` | What the script declares, printed in inspect mode |

## Seeing what a script declares

```bash
python stamp.py --rf-inspect        # print RF_SCHEMA and exit
```

This is the one thing a script does when you run it yourself, and it is the same thing the service does when a plugin is installed: import the file, collect the declarations, print them. What the submitter will show is something you can read in a terminal before anyone installs anything.

A script is not otherwise runnable as a program. It runs as a task, where the values, the node, its installed software and the farm's path mapping are all bound before your code sees them. None of that exists in a terminal, so a local run could only ever prove that the file imports.
