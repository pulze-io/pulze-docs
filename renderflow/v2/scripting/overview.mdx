A render farm runs work on many machines and reports back what happened. Rendering is the usual job, but a step can just as well be your own script: a shell command, a Python script, or a plugin packaged for the whole studio.

This page is about writing that code, so it runs on the farm. To drive RenderFlow from the outside instead, submitting jobs, reading status, reacting to events, see [Developers](/renderflow/v2/developers/overview).

## Choosing

| You have | Use |
|---|---|
| A command or script that already works | A **Shell step** |
| Work that has to spread across machines | A **Python step** |
| Work that has to report progress or fail one item without failing the rest | A **Python step** |
| Something the studio will submit again and again | A **plugin** |

The honest summary: start with a shell step, move to Python when you need the farm to divide the work, and turn it into a plugin when other people need to submit it without knowing where the script lives.

A plugin is a Python step with a name, an icon and a manifest. Nothing you learn writing one is wasted on the other.

## What is true of all three

**Your code runs on the machine that took the task, not on the server.** That is the whole point, and it is also the source of every surprise. The machine may be Linux while you wrote the script on Windows. It may not have the drive letter you used. It will not have your environment variables.

**A step's files are staged into the repository first**, unless **Save to repository** is cleared on the step, or a project synced from Perforce has **Project source** set to **Render in place**. That is why a render node can read a scene an artist saved locally. If your script needs a file that was not staged, it needs a path every machine can reach.

**A script step distributes only once it has a work list.** Without one it is a single run on a single machine. A plugin plans one with `@rf.tasks`, and a Python step is given one through the REST API; either way the farm splits it into tasks, hands them out, and retries the ones that fail. That is the same machinery a thousand-frame render uses.

**Nothing is added to `sys.argv` or the environment behind your back.** The Arguments field is the whole of a script's arguments. RenderFlow adds the `RF_*` variables, [listed in full](/renderflow/v2/scripting/shell-steps), and the variables set in the job's **Environment** section and for the application in **Settings → Apps**.

## What a step can find out

Any script, in any language, can read where it is and what it belongs to:

| | |
|---|---|
| The job | id, name and status |
| This step | id, name and position in the chain |
| This task | id and index, which is the frame number for a render |
| The machine | id and hostname |
| Earlier steps | what they produced, so a step can work on the output of the one before it |

A shell step reads these as environment variables. A Python step gets the same facts as objects, plus the applications installed on the machine and the tools RenderFlow ships. The [`rf` reference](/renderflow/v2/scripting/rf-reference) is the complete list.

<Note>
Scripts are not sandboxed. A step runs with the permissions of the account the RenderFlow service runs as, which on an unattended node is usually a service account with access to your storage. Treat the ability to submit a script step as the ability to run code on the farm, and see [Authentication](/renderflow/v2/developers/authentication) for who can do that.
</Note>
